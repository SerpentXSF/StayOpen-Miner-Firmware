## This release is the web interface, again

**No C source changed between 2.0.35 and this release.** `git diff
v2.0.35..HEAD` over `*.c`, `*.h` and `components/` is empty, and neither the
partition table nor `sdkconfig` moved apart from the version string. Nine
files changed in all: four in the web interface, two in the release tooling,
two documents, and this file.

So the file that carries this release is **`-www-ota.bin`**. The application
image is rebuilt because the version string is compiled into it, and that
string plus the build stamp should be the whole of the difference.

Nothing here fixes a defect a pool can reach, and nothing here changes how the
miner hashes. What it changes is what the dashboard tells you when something
is wrong, in one case where it said nothing and one where it said the wrong
thing.

## A dead pool looked exactly like a working one

The dashboard had no alert for a pool that is not connected. There was nothing
to read it from, either: the hashrate stays up, because the other pools absorb
the work; the badge beside the pool card says `waiting`, which it also says
during a normal start-up; and the share counters simply stop moving, which
takes a while to notice and longer to be sure about.

A miner submitting to nobody and a miner working correctly produced the same
page.

Now a disconnected pool raises an alert that names it. Three conditions guard
it, and each one is a case where the alert would otherwise be the thing that
is wrong:

- **The miner has to have reported the session.** Interfaces are served from
  the device, so this page also runs against older firmware that does not
  report pool sessions at all. An unreported session reads as *unknown*, not
  as *down* — otherwise a miner that is mining perfectly would carry a
  permanent "not connected".
- **A secondary pool only counts while dual mining is on.** A pool that is
  configured but switched off is not connected, and is not meant to be.
- **Nothing is said in the first minute of uptime.** Every boot passes through
  not-connected on its way to connected. An alert that fires on every boot is
  one you learn to scroll past, which costs you the one time it matters. If
  the age of the reading cannot be established, the page stays quiet for the
  same reason.

It deliberately does not guess from the hashrate or the share counters. A pool
can be connected and taking no shares for reasons that are not a fault, and a
miner can be hashing with a pool down. Only the session flag answers the
question that is being asked.

What happens to a dead pool's work has not changed, and is worth knowing
alongside the alert: the share of the slices assigned to a pool that is down
keeps being assigned to it, fails a liveness test at the moment the job would
be built, and falls through to pool A. The work is not lost, but it is not
shared out among the other live pools either. That is deliberate — zeroing a
disconnected pool's weight would hide the shortfall, where leaving it makes
`Jobs Selected` outrun `Jobs Served` by exactly the amount that pool is
costing you. The alert now tells you which pool to read those numbers about.

## The failover alert spoke for a pool that was not there

2.0.35 added an alert naming any pool mining on its failover endpoint rather
than the primary you configured. It did not check whether the failover
endpoint was answering.

So a pool that had stepped to a failover which was *itself* unreachable was
described as **"Mining on a failover endpoint, not the configured primary"** —
a sentence that says the miner is working, about a pool that is doing nothing.
Of the two problems in this release that is the worse one: silence makes you
look elsewhere, but a confident wrong answer stops you looking at all.

The failover alert now speaks only for pools that are actually connected, and
the new alert above covers the rest. The two can never name the same pool, so
there is no state in which the page tells you that one pool is both down and
working.

## It reported you ahead of a release it could not read

The Web Version row compares the interface version in a release against the
one installed. It had no way to say *I could not read that*: the comparison
returned a plain older-or-not answer, an unparseable version sorted as 0.0.0,
and so every release whose interface version could not be read came out as
**you are ahead of it** — the same answer a genuinely newer interface gets.

With 1.6.7 installed, all four of these reported the same thing:

| What the release said its interface was | Reported |
| --- | --- |
| `...` | you are ahead |
| `unknown` | you are ahead |
| `N/A` | you are ahead |
| `1.6.6` — a real, older version | you are ahead |

The first row is not hypothetical. `...` is what 2.0.35 published, for the
reasons that release's own notes set out, so this is the state a 2.0.35 miner
was actually in. Those three now report that the release's interface version
could not be read, and a genuine older version still reports correctly.

This one only ever misled owners who were up to date, which is why it survived
two releases that were looking straight at it.

## The interface version itself, which was wrong on this branch for a day

The interface version is `1.6.8 20261111`, up from `1.6.7 20261105`.

It should have moved twice already. Both interface changes above landed with
this string untouched, so for part of a day the published branch and the two
boards here served materially different interfaces that both answered to
`1.6.7 20261105`. That is the same confusion that caused 1.6.6 to be skipped
on purpose, and the comment above the version in the source had already warned
about it in writing — twice. The warning is now a rule stated in the place the
mistake gets made: the commit that changes anything under the interface source
bumps the version in the same commit.

Nobody outside this branch could have been affected, because neither change
had been released. It is recorded because the near miss is the interesting
part: nothing in the build, the typecheck or the release tooling noticed, and
the three interface-version defects in 2.0.35 and this release were all found
by reading rather than by anything that fails.

## Not on your device: the release tooling

Two of the nine changed files are `tools/ship.py` and a new test beside it.
They do not ship to the miner and you do not run them, but this is the second
release in a row whose notes have to mention the tooling, so it is worth
saying what was wrong.

The marker that carries the interface version into a release body was being
written loosely and read strictly. The tool matched marker-shaped text
anywhere in the body — including inside a code span in the middle of a
sentence — while the interface requires it on a line of its own and takes the
last one. A release whose notes merely *discussed* the marker could therefore
satisfy the tool's "this is already correct, leave it alone" path and ship with
nothing the page could read, which is the same failure 2.0.35 was cut to fix,
arrived at from the other direction.

The two patterns are now deliberately different, with the reason recorded
beside them: the loose one is character-for-character what interface 1.6.5
shipped, and every miner still on 1.6.5 or earlier reads release bodies that
way, so the tool has to keep asking the loose question in order to refuse.
There is now a test that lifts the pattern out of the interface source and
judges the tool's output against it, because the two tests this marker had
before both hardcoded a pattern, and both passed while it was broken.

## What was not tested, stated plainly

- **No hardware was touched for this release.** No board was flashed, rebooted
  or reconfigured. The two miners here have been running 2.0.35 continuously
  throughout.
- **The alerts were not photographed on a board.** The built interface is
  served gzip-only, so it cannot be previewed outside the device, and a
  browser check needs a miner. What was done instead: the page's own decision
  logic was extracted from the source and executed against 19 constructed
  status payloads, covering both failover-on-a-dead-endpoint cases, the
  start-up window, unreported sessions, dual mining switched off, and two
  pools down at once; and a separate check confirms every alert string the
  page asks for exists in both the English and Chinese tables, with the
  substitution token present in both. Against a copy of the page with only the
  failover gate removed, two of those cases fail by naming one pool in both
  alerts at once.
- **Nothing here was observed against a real disconnected pool.** The
  conditions are reasoned from what the firmware reports and tested against
  payloads, not against a pool that was taken away mid-run.

## Still open

Unchanged from 2.0.35, and none of it addressed here:

**Free internal RAM reaches a few hundred bytes at some point in every boot** —
lowest measured 131, cause unknown, measured across ten reboots rather than
inferred from one.

**Pool A's transport can still be destroyed by another task while its owner is
reading it.** It wants a lock and has not got one.

**The `esp-aes` allocation failure on a BC04 is unchanged and still
unexplained.** Two candidate explanations have been retracted;
`docs/KNOWN-ISSUES.md` records both.

**The pool split still reads pool A as a weight in one place.** Pool A is the
slider, and a weight set on a secondary cannot take anything from it; all-zero
weights are not an even four-way split.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place, and for this release
**`-www-ota.bin` is the one that matters** — it should be the only file whose
contents changed. `SHA256SUMS` covers every file here; check it before you
flash something you downloaded.
