## A pool could crash your miner, and so could anyone on the path

Four defects, all found by a review on 2026-10-17, all **pre-existing**. None
of them arrived with 2.0.31; every one is in that release and in the releases
before it. Two of them make a line this project has been publishing since
2.0.30 untrue, and that line is struck through in `docs/KNOWN-ISSUES.md` rather
than quietly amended.

**Two of them stop the miner dead.** 2.0.30 fixed a genuine remote `abort()` —
a `mining.notify` carrying more merkle branches than the firmware could hold —
and the hardening that fixed it checks the array, the type and the string
pointer of `mining.notify` params 0 to 3 and every merkle branch. It earned the
comment above it: *a pool that sends nonsense gets its job ignored*. **The
hardening simply stopped at param 3.** Params 5, 6 and 7 — the version, the
target and the timestamp — were dereferenced raw, as were
`mining.set_difficulty` params[0] and `mining.set_version_mask` params[0]. A
notify with five parameters, or a `set_difficulty` with an empty array, panics
the board. Every parameter the firmware reads is now checked before it is used,
and a malformed message gets a warning and is dropped.

This needs no privilege and no credentials. Stratum V1 over `stratum+tcp` is
plaintext and unauthenticated in both directions, so the pool you chose can do
this, and so can anyone able to sit on the path between you and it.

**Deeply nested JSON reached the stack canary.** cJSON recurses one stack frame
per level of nesting, and the library's own ceiling is 1,000 levels — far past
what an 8 KB task stack survives, so the overflow arrives before the parser's
own limit ever applies. A nesting check now runs *before* the parser and
refuses anything past 16 levels, which is several times deeper than any real
stratum message.

**Sixty seconds of pool silence tore the session down.** This one cost shares
rather than uptime, and it is the subtlest of the four. `esp_transport_read()`
returns `0` when its own poll expires and `-1` when the peer really closes the
connection. Pool A's receive loop treated both as a close. So one quiet minute
destroyed the transport, abandoned every job in flight and forced a full
re-handshake — and the ten-minute socket timeout the code sets, and that the
comments describe, never applied at all, because the transport's poll always
fired first. Pool A now accumulates idle time and gives up only after ten
genuine minutes of silence. The secondary pool poller never had this bug; its
own comment says *a quiet pool is not a dead one*.

**A rejected share leaked eight bytes.** The reject path `strdup`'d the pool's
reason string twice and freed only the second copy. Eight bytes per rejected
share, permanently, against any pool that sends a reason with its rejection.

## The board now tells you why it restarted

`/api/system/info` gained two fields, next to `uptimeSeconds` because they
answer the question a short uptime raises:

| field | what it is |
| --- | --- |
| `lastResetReason` | what the silicon reported: `Power on reset`, **`Brownout reset`**, `Software panic reset`, `Task watchdog reset`, **`Power glitch reset`**, `CPU lockup reset`, and the rest |
| `lastRestartReason` | the reason the firmware stored before a restart it chose to make, or `None` when it did not choose — which is itself the useful answer |

The firmware already worked all of this out at every boot and then only wrote
it to the log, where it scrolls away within minutes at debug level. On
2026-10-21 both of the boards here restarted inside the same minute and the
reason was simply gone by the time anyone looked — including whether it was a
brownout, which the firmware had known and discarded.

It answered its first real question on the day it shipped, and the answer was
dull: a check found the two boards at 2.04 and 2.10 hours of uptime, six
minutes apart, which is exactly the alarming shape of the 2026-10-21 event.
Both said `Software reset` / `Firmware update complete`. They were the two OTA
flashes of this build, minutes apart. That reading would previously have cost
an evening and ended in a guess.

**It records the last reset only.** A board restarting in a loop overwrites the
field every time, so catching a loop still means comparing uptime between
samples rather than reading one.

## Smaller things

A memory leak at every boot: the custom restart reason is read from NVS with a
function that returns allocated memory on every path, including its defaults,
and that copy was never freed.

The release tooling was reviewed and nine gaps closed, which matters to you only
in that this release is less likely to be wrong: the version the flasher
advertises is read from the source rather than guessed from whatever is lying in
the build directory, the checksum file no longer covers itself, stale binaries
cannot be swept into a release, and the published flasher now carries `LICENSE`
and a `SOURCE.txt` naming the exact commit beside the binaries it serves. It had
been serving about 12 MB of GPL binaries with neither.

## Still open

**Pool A's rejected shares are still not explained.** Every rejected share on
both boards, across every soak this project has run, has belonged to pool A;
pools B, C and D have never rejected one on either board. The 60-second
teardown above was the leading suspect, and **it is not the whole answer**:
this build has rejected 14 shares on the BC01 and 3 on the BC04, reported by
the pools as `Above target` and `Stale`, both ordinary stratum outcomes.

They arrived early in the run and then stopped. Across a later four-minute
window both counts stayed put while 60 and 62 shares were accepted, so this
looks like a cluster while difficulty settled rather than a steady rate — the
first reading, taken on its own, suggested a rate about eighteen times the
soak's and that reading was wrong. **This is an observation, not a result:**
two hours is not a soak, and the next one will say more than this can.

**A dead pool's share of the slices is lost rather than redistributed.**
Fallthrough is one way, secondaries to pool A; if a secondary goes down its
turns are skipped and nothing takes them. Deferred deliberately.

**The browser flasher's Update mode has still never been run on hardware**, in
either direction. It is the one path in the flasher that nothing has exercised.

**The Pool settings page has still never been looked at on the rendered page.**
The dashboard was confirmed by the owner on a real browser; the settings screen
is a different page, and it is the one where a mislabelling was found before.

**Free internal RAM reaches a few hundred bytes at some point in every boot** —
measured over ten reboots, lowest 131 bytes. It never approaches that again
while running, and the cause is not known. Finding it needs boot-stage
instrumentation.

**Pool A's transport can still be destroyed by another task while its owner is
reading it.** This is why the API's drop endpoint refuses pool A. It wants a
lock and has not got one.

## Testing

**26 hours on a BC01 and a BC04 together, with 0 reboots on either board** and
63,110 accepted shares between them. Free internal heap was *flatter* than
2.0.31: on the BC04 the per-quarter means were 14,147 / 13,257 / 13,279 /
13,223 bytes — one settle from a high boot and then 34 bytes of movement across
the last three quarters, against 2.0.31's steady 461-byte decline across the
whole run. DMA heap went +28 bytes/hour against 2.0.31's -23, and its floor
ended at 607 bytes rather than 311. A least-squares slope over the whole window
reads *worse* (-43 b/h against -23) purely because the first quarter's settle
drags the fit; the quarter means are the honest summary and are given here
instead.

**The two crash fixes were provoked, not reasoned about.** Five malformed
stratum lines were injected at a live miner, one per guard: a five-parameter
`mining.notify`, an empty `mining.set_difficulty`, a `set_version_mask` with no
parameter, a mistyped parameter, and JSON nested past the limit. Each was
refused by its own guard with its own warning and the miner carried on hashing
throughout. A control line was sent in the same run — a job id containing
square brackets, which is unusual but legal — and it was **accepted and
mined**, which is the half of the test that shows the guards are not simply
rejecting everything.

**The receive-timeout fix was measured by making a pool go quiet.** A stand-in
Stratum server held pool A silent for 180 seconds. The session survived it and
logged `pool quiet for N s` at exactly 60, 120 and 180 seconds — the three
points at which every earlier release would have destroyed the session, with
the first of them being the one that used to do it.

**The reset-reason fields were verified on both boards** after an over-the-air
update, past the 60-second rollback window, reporting `Software reset` and
`Firmware update complete`. That second value is the one that has to be copied
out of NVS before the key is cleared, so reading it back proves the ordering.

**What was not tested, stated plainly.** The reset-reason change landed *after*
the 26-hour soak, so unlike 2.0.31 **the binaries this release ships are not
the binaries that were soaked**. That change is additive — two JSON fields, two
file-scope strings and a `free()` — it was verified on both boards, and it has
a couple of hours on them, and that is the whole of its evidence. The browser
flasher's Update mode is still untested on hardware. Nothing has provoked a
genuine socket write failure. The `esp-aes` allocation failure on a BC04 is
unchanged and still unexplained; the explanation three releases gave for it was
withdrawn on 2026-10-19 and `docs/KNOWN-ISSUES.md` records why.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place. `SHA256SUMS` covers
every file here; check it before you flash something you downloaded.
