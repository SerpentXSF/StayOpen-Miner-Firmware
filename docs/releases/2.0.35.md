## Read this before you flash

This is unofficial firmware. It is not affiliated with, endorsed by, or
supported by Hammer, and flashing it may void whatever warranty you have.
It comes with no warranty of any kind — GPL-3.0 sections 15 and 16 apply,
and they mean what they say. You run it at your own risk, including the risk
that the flash itself leaves the device unusable, and including anything that
follows from running the hardware past its limits.

## This release is the web interface

**No C source changed between 2.0.34 and this release.** `git diff v2.0.34..HEAD`
over `*.c`, `*.h` and `components/` is empty. Everything here is in the web
interface, the release tooling, the commit hook and the documentation.

So this is the opposite of 2.0.34, which was application-only. The file that
carries it is **`-www-ota.bin`**. The application image is rebuilt because the
version string is compiled into it, and that string plus the build stamp is
the whole of the difference.

Nothing here fixes a defect a pool can reach. 2.0.34 is still the release to
be on if you are behind; this one fixes what the interface *told* you, and one
thing it could not do at all.

## A miner with a password could not be updated from its own page

Found on 2026-11-04 when an owner could not update a BC01 from its own web
interface: both images, three automatic retries each, every attempt failing
with *Upload failed! Do not close this page.*

**The upload never sent credentials.** Every other call the interface makes to
the miner goes through one shared axios instance, whose request interceptor
attaches `Authorization: Bearer <token>` from `localStorage`. The OTA upload
was the one exception — it used the bare `axios` import, so no interceptor ran
and no header was attached.

`api_auth_require()` accepts nothing else. Not a cookie. Not the `?token=`
query parameter, which exists only for WebSockets, because a browser cannot
set a header on one. So the miner answered **401 before reading a byte of the
body** — measured at 0.1 s against a 2,855,041-byte post.

This is deterministic, not an intermittent transfer problem. Every image,
every retry, on **any miner that has an API password set**. It went unnoticed
because a miner with authentication disabled takes the `auth_disabled`
short-circuit and uploads fine, which is how this path worked before token
login arrived in web 1.2.0.

Fixed by attaching the token the rest of the interface already uses, and
confirmed in the built bundle rather than only in the source.

**Two theories that were wrong are in `docs/KNOWN-ISSUES.md`, with the changes
they produced and the fact that both were taken back out.** One of them —
socket LRU purge — survived an eviction test and was still wrong, because
`esp_http_server` has a single task that never reaches `accept` while it is
inside the OTA handler, so the purge cannot fire during an upload at all. The
other is unresolved and labelled as such: a 401 at 0.1 s does not obviously
match a progress bar that reached 78.9%. The code path is unambiguous and the
fix is right, but that figure is not explained and no explanation is claimed.

One real thing the failed experiment did establish: **while an upload is
running the miner accepts no new connections** — three attempts, all timed
out. The interface going unresponsive during an update is expected, not a
symptom.

## How to install this, since the path it fixes is the broken one

If your miner has an API password and you are on 2.0.34 or earlier, **its own
page cannot install this release.** That is the defect above, and it has to be
worked around once. In order of preference:

1. **The browser flasher's Update mode**, over USB. It does not use the
   authenticated endpoint at all, and it was run on hardware on 2026-11-03 —
   a configured BC04, 2.0.33 → 2.0.34, erase box left unticked, settings kept:
   it rejoined its own WiFi unaided and still accepted its stored API
   password. Leave the erase box unticked and your settings survive.
2. **`tools/push_ota.py` from a workstation**, which sends the header
   correctly. It now also reads `DeviceModel` from the miner and refuses an
   image built for the other board.
3. **Clear the API password, update from the page, set it again.** This works,
   and while the password is cleared every endpoint on the miner is reachable
   without credentials by anyone on your network. It is third for that reason.

If your miner has no API password, the page's Browse-and-upload path has
always worked and still does.

**If you install in place, do the application image first**, and give it more
than 80 seconds of uptime before you upload the web image. The application
rolls back if it restarts inside a 60-second confirm window
(`OTA_CONFIRM_SECONDS` in `main/system.c`), and a second upload restarts it.

## The Web Version row advertised an update that did not exist

The same owner was sent after a web update that was already installed.

The row compared the release **tag** against the running **firmware** version.
That was deliberate — comparing the interface's `1.6.4` against a `2.0.34` tag
reads as newer forever — but the side effect is that on an application-only
release the interface row still showed an upgrade arrow. 2.0.34 is exactly
that, its web image being byte-identical to 2.0.33's, so the badge was
advertising nothing.

The interface carries its own version series, so the only honest comparison is
against another web version, and a release did not publish one. **This release
does**, and so will every release after it: `ship.py` appends
`<!-- stayopen-web-version: ... -->` to the notes it uploads, read from
`const.ts` so it cannot drift from what was built. It rides in the release
body, which `api.github.com` serves with CORS headers.

The row now says one of three things: an update is available, **unchanged in
this release**, or — for every release up to and including 2.0.34, which carry
no marker — that the release does not say. The last is the truthful answer
rather than a guess.

`WEB_VERSION` is `1.6.5 20261104`. It had not moved from `1.6.4 20261003`
across two rounds of interface changes, which did not matter while nothing
compared it.

## "Install Web Update" was a promise a browser cannot keep

Both `Install Web Update` and `Install Firmware Update` existed in both
languages and were referenced nowhere. The only control on either row was
`Download`.

They were never wired because in a browser they cannot be. Measured:
`api.github.com` sends `Access-Control-Allow-Origin: *`; the release asset and
its redirect target send **none, on either hop**. A page served from your
miner may send that request but may not read the response, so it can never
hand the bytes to the OTA endpoint.

The dead strings are gone and each Download button now carries the real next
step. One-click install would need the miner to fetch the file itself — an
authenticated endpoint taking a URL, with the firmware doing the HTTPS GET.
That is a real feature with real exposure and is not attempted here.

## "Your firmware is up to date" when it could not reach GitHub

The worst of this release's reporting bugs, because it is the one an owner
acts on. The check asked GitHub with `Promise.allSettled`, which **never
rejects** — a failed request comes back as a settled result with
`status: 'rejected'`. Nothing read that status, so both requests failing left
the result identical to "asked and found nothing" and printed *Your firmware
is up to date.* The `catch` meant to handle it could not fire, because
`allSettled` had nothing to throw.

A miner on an isolated network, behind a DNS failure, or rate-limited by
GitHub told its owner they were current. It matters most at exactly the wrong
moment: 2.0.34 fixes five defects a pool can reach without credentials, and
the owners least likely to hear about it are the ones whose miner cannot reach
GitHub. There are three answers now — an update exists, there is none, and it
could not ask — and the third says in so many words that it is not a
confirmation.

## The pool page could hide a pool that was mining

The mode selector derived Solo/Dual/Quad from **how many** secondary hosts
were filled, which is not the miner's rule: the firmware connects every pool
that has a host and does not care about the gaps.

A configuration with C filled and B empty counted as 2, which is Dual, which
shows one secondary panel — so the page showed an empty B, hid C, and C went
on mining. Pressing **Save** wrote what the page showed. B+C counted as 3,
which matches none of the three buttons, so nothing was selected at all. Four
of seven configurations were wrong. The rule now reaches the highest-lettered
configured pool, and is right on all seven.

**A Share weight also kept dividing the work after its field was hidden.** The
Weight input is hidden below two secondaries, on the reasonable ground that
with one secondary the A/B slider says the same thing — but the stored value
survived. Set B to 25 in Quad, drop to Dual, and the split still normalised
pool A's percentage against that 25: a slider reading A 50% ran A at 67% and B
at 33%, from a number the owner could no longer see. The page now zeroes a
weight it will not show, on a mode change and on load, which also makes the
Dual slider exact.

That is not the pool-split defect under **Still open** below and does not fix
it. It stops the page feeding that code a hidden input.

## The Chinese interface, and the security page

**The Chinese interface printed key paths where text belonged.** `createI18n`
had no `fallbackLocale`, and vue-i18n renders a missing key as the key path
itself. `zh.ts` was four keys short of `en.ts`, three of them on the
dashboard's Ethernet pill, so a BC04 in Chinese displayed the literal string
`dashboard.card.ethernet_status` next to `dashboard.card.eth_on`. The keys are
filled in and the fallback is set: the keys matter now, the fallback matters
next time, because the way this happens is `en` gaining a key while `zh` is
not touched in the same change.

**The security page was English only, including the part that matters.** Every
string on it was written in English in the source — including the alert saying
this miner has no password, and the confirm that asks you to agree that
clearing it leaves every endpoint reachable without credentials. Those are the
two worst strings in the interface to leave in a language the reader may not
have, because misreading either one leaves a miner open on its owner's
network. Both languages now.

**And a fan at 100% no longer says "Simulator"**, which described nothing —
the firmware has no mode of that name and nothing in it treats 100% as a
simulation. The warning worth giving at that setting is that there is no duty
left above it.

## The release tooling, which owners do not run but are downstream of

Seven guards, on the path that publishes these binaries. The ones that bear on
what you receive:

- **`--push` was held to weaker checks than `--github`.** Pushing the flasher
  force-pushes `gh-pages`, which serves `-full.bin` to anyone with the URL,
  with no release and no checkout in between — so a push from a dirty tree
  published firmware whose own `SOURCE.txt`, served from the same directory,
  admitted it was not built from any public commit. On a GPL-3.0 project that
  is a compliance problem, not untidiness. The source checks now run for
  either flag.
- **`SOURCE.txt` could be published saying `commit unknown`.** Naming the
  commit is that file's whole job, so it now refuses to be written without
  one.
- **The flasher's manifest guard was not the check its comment claimed.** It
  caught a partition starting at or before `nvs` and running into it, but a
  partition starting anywhere *inside* `nvs` passed — 4 KB written into the
  middle of your settings, by the manifest whose label promises to keep them.
  It is an interval intersection now, and `nvs`'s extent is read from
  `partitions.csv`.
- **A stated version was compared as a substring of the image filename**, so
  `2.0.3` passed against a `2.0.33` image.
- **A timed-out OTA push reported success**, so `push_ota.py app && push_ota.py
  www` would push the web interface of a version that never installed.
- **The credential guards never matched pool B, C or D.** They listed the API
  spelling `poolBPass`; an NVS image only ever holds the lowercase
  `poolbpass`. That entry matched nothing, for every pool, since quad pool
  landed — and it named B only, so C and D were never in it even by
  intention. Both the commit hook and the release packager use patterns now.
- **`push_ota.py` refuses a board/image mismatch.** It reads `DeviceModel`
  from the miner before anything is uploaded and takes the board from the
  release filename. The boards do not share an ASIC pinout, so the mistake it
  prevents leaves a miner that boots, serves its interface, detects its chip
  and never returns a share.

## What was not tested, stated plainly

**The fixed interface has not been loaded in a browser.** It builds, and
`vue-tsc` passes, on both boards. The two boards were held on published 2.0.34
rather than run on an unreleased build, so nothing was flashed to see it.

What *was* measured: the 401 (0.1 s, before any of the 2,855,041 bytes are
read), authenticated uploads from a single-connection client succeeding three
times out of three — 37 s, 21 s, 37 s — across both the application and web
endpoints, the CORS results on both hops with an `Origin` header, and the fix
present in the built bundle rather than only in the source.

**This is also the first release cut through the reordered `ship.py` path**,
and the first to carry a web-version marker. Both were reasoned from the code
until now.

## Still open

Unchanged by this release, and none of it was expected to move.

**Pool A's rejected shares are still not explained.** One 137-hour BC01 boot:
135,188 accepted, 35 `Above target`, 71 `Stale`. The burst at the start is
real and dominates — 6.2 `Above target` per hour early against 0.26 per hour
over the session — but there is a **residual** of roughly one every five hours
afterwards, which is why the earlier conclusion that it "ends" was withdrawn
for the third time. Rates: `Above target` 0.026%, `Stale` 0.053%, 0.078% of
shares in total.

Whether that residual is a small fresh burst on each pool reconnect or a
steady trickle is undetermined, and `sharesRejectedReasons` cannot settle it —
it is a running total with no timestamps, so any "it stopped" read off it is
really a statement about when it was read. `watch_rejects.py` would answer it
and has never been pointed at the question.

**Pool A's slider does not do what the page says in every configuration.** The
secondary Share weights are normalised against pool A's own percentage rather
than dividing the remainder, so pool A keeps its stated share only when the
secondary weights happen to sum to what is left over. This is in the firmware,
not the page, and wants a soak of its own.

**A dead pool's share of the slices is lost rather than redistributed.**

**Free internal RAM reaches a few hundred bytes at some point in every boot** —
lowest measured 131. Cause unknown.

**Pool A's transport can still be destroyed by another task while its owner is
reading it.** It wants a lock and has not got one.

**The `esp-aes` allocation failure on a BC04 is unchanged and still
unexplained.** Two candidate explanations have been retracted;
`docs/KNOWN-ISSUES.md` records both.

**Two credential files hold one password.** `secrets/bc01-api-password.txt`
and `secrets/bc04-api-password.txt` are byte-identical, so passing the wrong
one still logs in and proves nothing about which board answered. That looks
like a safeguard and is not one. Not fixed here because it is not a code
decision: either they should be one file or the boards should have different
passwords.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place, and for this release
**`-www-ota.bin` is the one that matters** — it is the only file whose
contents changed. `SHA256SUMS` covers every file here; check it before you
flash something you downloaded.
