## Update promptly, and the reason is not a crash

Five defects, found by a review on 2026-10-26, all **pre-existing**: every
release up to and including 2.0.33 has all five. None of them arrived with
2.0.32 or 2.0.33.

**One of them lets a pool write its own bytes over the return address of a
running task.** `mining.submit` was built with `sprintf` into a 2300-byte array
that lives on the stack of a task created with 6144 bytes of it. The job id in
that message is the pool's, and the hardening added in 2.0.32 checks every
parameter's **type** while saying nothing about its **length**.

So a `mining.notify` carrying a 3,000-character job id, followed by a
`mining.set_difficulty [1]` so a share turns up within seconds, writes past the
end of that array on the first share found against that job. It writes
**upward**, over the saved registers and the return address. The FreeRTOS stack
canary guards the **low** end of a task's stack and never sees a write going the
other way.

Whether that can be turned into running chosen code on the device has not been
established here and is not claimed. What is certain is that it is memory
corruption, with pool-controlled contents, triggered from the network.

**This needs no credentials and no privilege.** Stratum V1 over `stratum+tcp`
is plaintext and unauthenticated in both directions, so the pool you chose can
do it, and so can anyone able to sit on the path between you and it. The same
function serves pools B, C and D.

Fixed with `snprintf` and the truncation result checked, in all four places a
message is built, so a share that will not fit is refused with a log line rather
than built. The notify guard also now refuses a job id longer than 128
characters — real pools use 8 to 64 — so a job whose shares could never be
submitted is dropped where that can be said plainly.

**A pool that merely refuses to subscribe could make the miner free the same job
twice.** The subscribe-result parser had two `goto` jumps that landed *after*
the line's method was assigned. Both callers reuse one message struct for every
line of a session, so a line that jumped left the **previous** line's method in
place and the caller acted on it: pool A wrote through a job the work queue
already owned and handed it over a second time — a use-after-free, then a double
free. The secondary pools got a NULL dereference instead, which is a panic
rather than heap corruption.

No misbehaviour was needed to reach it. A pool refusing `mining.subscribe` with
the ordinary `{"id":2,"result":null,"error":[20,…]}` lands in that branch, and
the old code jumped. A banned address was enough.

It is fixed in two places on purpose. The parser now validates before it assigns
anything and resets the method where it fails instead of jumping past it, and
pool A's task now clears its job pointer after handing it to the queue — two
lines the secondary path has always had. The second is not the fix; it turns
that whole class of mistake into a loud NULL dereference instead of silent heap
corruption, which is worth having regardless.

**`mining.set_extranonce` had three ways to panic the board** — a non-string
extranonce, a one-element parameter list, and a parameter list that is not a
list — and it leaked memory on each malformed message, out of the internal pool
that already runs down to a few hundred bytes free on every boot.

**A `mining.configure` reply with a non-string version mask** went straight into
`strtoul` on a NULL pointer.

**A pool that never sent a newline rebooted the board.** Neither receive path
put any limit on the line it was accumulating, and both call `esp_restart()`
when the allocation finally fails. So "connect and send bytes forever without a
newline" was a remote reboot, repeatable on every reconnect. Both paths now stop
at 16 KB — a real notify with a full merkle branch list runs to about 3 KB — and
drop the connection instead, which the caller already handles by reconnecting.

## Which file carries it

All five are in the application. The web interface is **unchanged from 2.0.33**,
so if you are on 2.0.33 the application image is all you need: `-ota.bin`, or
`-full.bin` and the browser flasher, which write everything anyway.

## What was not tested, stated plainly

**These fixes were built clean on both boards and have not been run on
hardware.** That is the whole of the evidence behind this release, and it is
weaker than the release it supersedes.

2.0.32's four equivalents were each provoked deliberately at a live miner — five
malformed stratum lines, one per guard, plus a legal-but-unusual control line
that was accepted and mined to show the guards were not simply refusing
everything. **That was not done for these five.** The two boards here are being
held on 2.0.33 on purpose, so that the browser flasher's Update mode — the one
path in the flasher that nothing has ever exercised, in either direction — has a
version to move them to.

So this release is published on a reading of the code and a clean build. The
defects it fixes are remotely reachable without credentials, which is why it is
not being held until a board is free; that is a judgement, and the evidence
behind it is stated here rather than left to be assumed.

**One behaviour change, which is a change and not only a fix.** The extranonce2
length must now be a JSON number. A pool sending it as a string used to be
accepted, with the length reading as zero, so the session came up and then mined
against an extranonce2 length of nothing. It will now be refused and the session
reconnected. That is the better of the two failures, but it turns a quietly
broken pool into a visibly reconnecting one. Standard Stratum V1 sends a number
and nothing here has been seen to do otherwise.

## The 2.0.32 claim this release corrects

`docs/KNOWN-ISSUES.md` has carried a row saying a pool cannot crash or reboot
the miner. It was struck through for releases up to 2.0.31, restored as a
positive statement in 2.0.32, and **it was wrong again.** 2.0.32 closed the
paths that review read.

This is the third time the same defect has been walked: params 0 to 3 hardened
in 2.0.30, params 5, 6 and 7 in 2.0.32, and now the output side entirely. Each
pass took the previous one's scope as the boundary. The row is not being
restored this time; the entry says which paths have been checked and by whom,
and leaves the general claim unmade.

## Still open

Unchanged by this release, and none of it was expected to move.

**Pool A's rejected shares are still not explained.** Measured properly on
2026-10-26 for the first time: 9 rejects on a BC01 in the first six minutes
after a flash, all `Above target`, then the count unmoved while 144 further
shares were accepted. So it is a start-up burst while the pool's difficulty
finds its level, not a persisting rate. Why it is always pool A is still
unknown.

**Pool A's slider does not do what the page says in every configuration.** The
secondary Share weights are normalised against pool A's own percentage rather
than dividing the remainder, so pool A keeps its stated share only when the
secondary weights happen to sum to what is left over. Found in the same review,
not fixed here, because it changes how work is divided and wants a soak of its
own.

**The browser flasher's Update mode has still never been run on hardware**, in
either direction.

**A dead pool's share of the slices is lost rather than redistributed.**

**Free internal RAM reaches a few hundred bytes at some point in every boot** —
lowest measured 131. Cause unknown.

**Pool A's transport can still be destroyed by another task while its owner is
reading it.** It wants a lock and has not got one.

**The `esp-aes` allocation failure on a BC04 is unchanged and still
unexplained.** One candidate explanation was retracted on 2026-10-19 and a
second was refuted on 2026-10-26: the ESP32-S3 can DMA from PSRAM, so only the
output buffer is bounced and the demand is one aligned block rather than two.
`docs/KNOWN-ISSUES.md` records both.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place, and for this release
`-ota.bin` is the one that matters. `SHA256SUMS` covers every file here; check
it before you flash something you downloaded.
