## Read this before you flash

This is unofficial firmware. It is not affiliated with, endorsed by, or
supported by Hammer, and flashing it may void whatever warranty you have.
It comes with no warranty of any kind — GPL-3.0 sections 15 and 16 apply,
and they mean what they say. You run it at your own risk, including the risk
that the flash itself leaves the device unusable, and including anything that
follows from running the hardware past its limits.

## This release changes one sentence of text

It is worth saying that first, because the version number is the same size as
2.0.32's and this release is not. **No firmware behaviour changed.** Nothing in
mining, Stratum, the pool handling, the API or the self test is different from
2.0.32. The application binary differs from 2.0.32's only in the version string
it reports.

The one change is in the web interface. Under **Pool settings**, the hint below
the **Share** field used to end:

> All at 0 shares that remainder evenly.

"shares" there is a verb, and it sits directly below a field labelled *Share*,
so a reader hits the word as the noun they have just been looking at and the
sentence comes apart. It now reads:

> If every secondary is 0, they divide that remainder evenly.

Same meaning, and it only parses one way.

**If you are on 2.0.32 and the old wording did not trouble you, there is
nothing for you here.** Nothing is fixed that affects hashing or stability, and
skipping this release costs you nothing that the next one will not give you.

## Which file carries it

The web interface lives in its own flash partition behind its own endpoint, so
**`-www-ota.bin` is the only file in this release that carries the change**. An
application update alone — `-ota.bin` — will move you to 2.0.33 and leave the
old sentence on the page.

The browser flasher and `-full.bin` write both partitions, so either of those
gets you everything in one step.

## Why cut a release for one string

Because the alternative was worse in both directions. Holding the fix until
something substantial arrives leaves a sentence that does not parse on the
settings page of the current release for however long that takes. Flashing it
to the boards here without releasing it — which is what was nearly done — leaves
this project's own hardware running an interface ahead of the one it publishes,
which is the state that makes "it works here" stop meaning anything.

A release costs a tag and an upload. The published surface matching the tree is
worth more than that.

## Still open

Nothing on this list moved in this release, and none of it was expected to.
It is repeated rather than linked because a release page that sends you
somewhere else to find the caveats is a release page that hides them.

**Pool A's rejected shares are still not explained.** Every rejected share on
both boards, across every soak this project has run, has belonged to pool A;
pools B, C and D have never rejected one on either board. The 60-second
teardown fixed in 2.0.32 was the leading suspect and is not the whole answer.
Both boards have been clean since the 2.0.32 flash, but their counters were
reset by that flash, so that is not yet evidence of anything.

> **Measured properly a few hours later, 2026-10-26.** Flashing this release
> reset the counters again, which made the minutes after a connect observable
> from the start. The BC01 rejected 9 shares in its first six minutes, all
> `Above target`, and then **the count sat at 9 while 144 further shares were
> accepted**; the BC04 took 179 and rejected none. So it is a start-up burst
> while the pool's difficulty finds its level, not a persisting rate. The
> 6-minute figure on its own reads as 12.8%, which is what you get for dividing
> a fixed burst by a short window — this is why the rule here is two samples
> before quoting a rate. Why it is always pool A is still unexplained.

**A dead pool's share of the slices is lost rather than redistributed.**
Fallthrough is one way, secondaries to pool A; if a secondary goes down its
turns are skipped and nothing takes them. Deferred deliberately.

**The browser flasher's Update mode has still never been run on hardware**, in
either direction. It is the one path in the flasher that nothing has exercised,
and it is the path an owner on 2.0.32 would use to get this release.

**Free internal RAM reaches a few hundred bytes at some point in every boot** —
measured over ten reboots, lowest 131 bytes. It never approaches that again
while running, and the cause is not known. Finding it needs boot-stage
instrumentation.

**Pool A's transport can still be destroyed by another task while its owner is
reading it.** This is why the API's drop endpoint refuses pool A. It wants a
lock and has not got one.

**The `esp-aes` allocation failure on a BC04 is unchanged and still
unexplained.** The explanation three releases gave for it was withdrawn on
2026-10-19 and `docs/KNOWN-ISSUES.md` records why. Worst owner-visible effect
is a stale price.

## Testing

**No soak was run for this release, and none is claimed.** 2.0.32 was soaked
for 26 hours and this release changes no code that a soak could exercise — the
compiled firmware is 2.0.32's with a different version string, and the only
edit is one entry in a translation table. Saying that plainly is the point:
2.0.32's notes had to admit that the binaries it shipped were not the binaries
it soaked, and this release is not going to quietly inherit that soak's
reputation for a build it did not cover.

What was actually checked:

- **The string is in the shipped bundle.** The web interface was built and the
  new wording found in the minified, gzipped asset the miner serves, with the
  old wording absent from it. Checked in the built artifact rather than in the
  source it came from, because the build is what reaches the board.
- **The page itself was confirmed on both boards on 2026-10-25**, on the
  rendered settings screen, by the owner from their own browser. That was
  2.0.32's interface — every failover block headed for its own pool, the
  four-ASIC gating correct, the split readouts matching the API rather than
  being read off the screen. It is this release's interface too, apart from the
  one sentence above.
**What has not been checked at the time of writing.** The two boards here are
on 2.0.32, so nothing has yet served this release's web asset to anything. The
published `-www-ota.bin` is going onto both of them straight after this release
is cut, verified against the release's own `SHA256SUMS` first so that what gets
flashed is provably what is published; the result will be added here, dated,
whichever way it goes. The rendered page needs a sign-in on a host that is not
local, so looking at it is the owner's part — the bytes are not.

> **Done 2026-10-26, within the hour.** Both boards are on the published
> 2.0.33, application and web, flashed from the release assets after their
> SHA-256 was matched against the published `SHA256SUMS`. Each was asked for
> the interface it serves: the reworded sentence appears once, in
> `/assets/index-BdsFUer3.js`, and the old sentence appears **nowhere** across
> all nine served scripts on either board — which is the half that matters,
> because a partly written partition would show both. BC01 came back hashing
> at ~1,485 GH/s and the BC04 at ~5,389 GH/s, unchanged.
>
> Two things fell out of doing it. `lastRestartReason` — the field 2.0.32
> added — read `Web interface update complete` on both boards, which is the
> second time it has answered a real question without anyone reading a log.
> And the `-www-ota.bin` is **byte-identical between the two boards**
> (`10922f54…`): the web partition has nothing board-specific in it, so the
> release publishes the same container twice under two names. Harmless, and
> worth knowing before anyone treats a BC01 web image and a BC04 one as
> different things.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place, and for this release
`-www-ota.bin` is the one that matters. `SHA256SUMS` covers every file here;
check it before you flash something you downloaded.
