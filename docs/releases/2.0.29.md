## The Ethernet controller is held in reset while the core rail switches on

A W5500 runs from its own supply. It is clocking, and linked if a cable is
attached, whether or not the firmware has opened it. Powering the hashboard
steps the core rail hard, and a controller that is live through that step is
the one failure mechanism this project has direct evidence for: a BC04 lost
here stopped answering about 70 ms after it, and the part was later found
shorted across 3.3 V.

2.0.28 closed the two software paths that brought Ethernet up early. It did
not depower the chip, so on 2.0.28 a cold boot with a cable attached was
reduced but not eliminated. This release drives the reset line low before
either path that powers the rail, so the PHY and its internal regulator are
off while it happens and an attached cable makes no difference — the part is
dark either way.

**If you run Ethernet on a BC04, this is the reason to update.**

## Also fixed

**Dual pool no longer builds work for a pool that has gone away.** With a
stale notify held in memory, the scheduler kept giving pool B its share of the
slices after a disconnect, and that work was thrown away — so a miner looked
like it was splitting as configured while part of its hashrate produced
nothing.

**A share can no longer be scored or submitted from a freed job.** The result
task read a job pointer without the lock that protects it, while the sender
was freeing and replacing that same slot. This one ships reasoned rather than
proven; see Still open.

**Five reset reasons that reported as "Not specified"** now have names,
including USB, power glitch and CPU lockup — the three that match failures
this project has actually chased. The numeric code is carried as well.

**The pin bridge test no longer reports stuck-low pins as shorts.** A pin
already held low reads low whichever line is driven, so three stuck pins were
being reported as 28 bridged pairs. That output goes into fault evidence,
where it buried the real finding.

## Still open

**The use-after-free fix is not proven.** The soak establishes that it does
not leak and does not destabilise anything, which was its most plausible
regression — but it does not show the race is gone, because an unfixed build
would very likely have produced the same numbers. The bug was frequently
silent while firing, and the symptom it does produce is booked as a hardware
error rather than a rejected share, which is indistinguishable from marginal
silicon without a per-core breakdown. What would actually settle it is in
`docs/2029-VERIFICATION-PLAN.md` section 3: a 24-hour run either side of the
fix compared on hardware-error rate and per-core distribution, and better
still a third build with heap poisoning. Neither has been run.

**The same corrections in `components/asic/lt0051.c` are reviewed and nothing
more.** That driver is off by default and matches no board here, so those
sites were never exercised.

**A BC04 still cannot de-energise its own hashboard once I²C is gone.** There
is no second lever to give it. A miner showing an empty bus scan, a board
temperature of −60 °C, or a reboot every four minutes should have its power
removed by hand.

Both of the above, with what is fixed and what is not, are in
`docs/KNOWN-ISSUES.md`.

## Testing

**Soaked 26 hours on a BC04.** 0 reboots, 0 hardware errors, one unreachable
sample from a Wi-Fi blip that recovered by itself, and free heap flat at −25
bytes per hour across 3,112 samples. Frequency and core voltage never moved
from 640 MHz / 4.60 V.

This is the first release whose soak recorded free heap from the start, so it
is the first that can say anything about a slow leak rather than only about a
miner that looked healthy while it was watched. The heap figure is the one
that matters for the job-pointer fix, which adds roughly eleven allocations a
second.

**The reset hold was verified on a working board**: held at 1.7 s, rail
stepped at 10.5 s, released at 14.5 s, controller answered, interface linked,
took a DHCP lease and carried 262 KB at 609 KB/s, so it passes real traffic
rather than merely linking.

**The cable was connected after the rail had settled, not before it stepped.**
Nothing has yet booted this board from cold with a cable already attached,
which is the exact shape of the original failure. What the hold does is leave
the PHY and its internal regulator off through the step, so an attached cable
makes no difference to what the part experiences — that mechanism is
demonstrated; the historical staging is untried.

**The dual-pool fix was verified across a 30/60/30 minute up-down-up test.**
While pool B was down, zero jobs were built for it, and every job the
scheduler selected for it went to pool A instead.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place. `SHA256SUMS` covers
every file here; check it before you flash something you downloaded.
