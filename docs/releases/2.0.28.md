## The fan-fault protection can fire now

It could not, and it could not in two independent ways, so fixing either alone
would have changed nothing. The check was passed a maximum fan speed of zero
and both of its comparisons were against that value, so it returned "fan is
fine" for any reading including zero RPM; and the shutdown behind it was gated
on a flag that is declared false and never assigned.

Underneath that, the fan controller reported success whatever happened — a
controller that had stopped answering looked exactly like a fan reading zero.

All three are fixed. The new check asks a deliberately narrow question,
because a false positive powers down a working miner: **a fan being driven at
30% or more and reporting no rotation at all, for five consecutive checks —
ten seconds.** A stopped or disconnected fan reads zero. A merely slow one
does not, and is left to the over-temperature trip, which is the protection
that actually matters and has always worked.

It only judges a fan that has reported a non-zero speed since boot, so a board
with no tachometer is never shut down for reading zero.

A failed fan read no longer panics the firmware either. That turned a fault it
could have acted on into a reboot loop — and a panic is the one response that
guarantees nobody turns the heat off first.

## The core-voltage cap holds now

The vendor caps a BC04 at 4.80 V across four BM1370s in series. That cap was
applied to the startup default and nowhere else, while `TPS546_VOUT_MAX` on
the same board is 5.20 — and every other path checked against *that*.

One NVS key brought the board up over the cap. All four voltage fields in the
settings API accepted anything below 5.20 and applied it live, storing it as
the value the miner returns on. Eight percent over, on a four-chip string,
from a single request.

Whether 1.30 V a chip harms a BM1370 is not something this project can answer,
and nothing here claims it does. That a cap existed and did not hold is
answerable. There is now one ceiling and all five sites ask it.

## When it cannot switch the hashboard off, it says so

`power_off_hashboard()` returned success whatever happened, so every
protection path — overheat, unreadable sensor, fan fault — logged "cut off the
power" and waited a hundred seconds without knowing whether it had.

It reports the failure now. On the BC01 family it falls back to the USB-PD
gate, which sits on a different bus and survives the I²C failure that takes
the regulator away. On a BC04 there is no such gate, so it says plainly in the
log that the hashboard may still be powered and asks for the plug to be
pulled. That is the whole of what firmware can do on that board.

## The web interface no longer goes unreachable while the miner keeps hashing

An owner reported the interface disappearing after some hours on a miner that
was visibly still working. Their log caught it twenty hours in.

The server holds eight sockets and was never told to reclaim them, so at eight
it refused new connections rather than dropping the least recently used. It
holds them for a long time, too: a browser tab killed without a close, a
laptop that slept mid-request, a phone that walked out of range. None of those
send a FIN, so the slot stays occupied until the receive timeout expires.

Mining never notices, because the stratum tasks own their own sockets. That is
what makes the symptom so misleading -- the miner is plainly fine and the
interface is simply gone, so the suspicion lands on the network.

It reclaims the oldest connection now.

## Both fan tachometers are reported

These boards have two fan headers and ship with one fan fitted, so one
tachometer reads 0 RPM on a perfectly healthy miner. Which one is not the same
across boards. Until now the firmware reported only the higher of the two, and
it took comparing three owners' boards by hand to establish that the zero was
an empty header rather than a fault -- nothing in the log or the interface
said which channel was which.

Now: `fanrpm0` and `fanrpm1` in `/api/system/info` carry the raw channels, one
line at startup names what each reads, and the dashboard shows a second fan
row when a second fan is actually turning. `fanrpm` keeps its existing
meaning, so nothing built against it changes.

This is reporting only. Nothing trips on a single channel, and the fan check
above is untouched -- on a board with one fan fitted, the reading it already
uses *is* that fan, and it fires correctly if it stops.

## Still open

**A BC04 still cannot de-energise its own hashboard once I²C is gone.** The
change above makes the failure visible rather than silent; it does not give
the board a second lever, because there isn't one. A miner showing an empty
bus scan, a board temperature of −60 °C, or a reboot every four minutes should
have its power removed by hand.

**Nothing trips on a single fan channel.** The stall check still judges only
the effective reading. Arming it per channel would need a board with two fans
actually fitted to test against, and none exists here; shipping an untested
fan trip is how the earlier board-wide tachometer latch nearly powered off a
healthy miner. The channels are reported so the question can be answered from
an owner's log instead of guessed at.

## Testing

Flashed to a BC01 and watched for three minutes: mining resumed normally at
about 1.4 TH/s, the fan sat at 82% and 4839 RPM, and no fan warning or trip
appeared in the log. That proves the new check does not fire on a healthy
miner, which was the risk worth testing.

**The positive case is untested.** Confirming that a genuinely stalled fan
trips the shutdown means stopping a fan on a running miner, which was not
done. The logic is straightforward and the guard against false positives has
been exercised; the trip itself has not.

The voltage ceiling changes nothing on a BC01, whose ceiling is unchanged, so
that fix is **untested on hardware** — it needs a BC04. **No BC04 has run any
of this firmware.**

**The two changes added after that run are untested on hardware.** The socket
reclaim and the per-channel fan reporting both build clean for BC01 and BC04,
and neither has been on a board. The fan reporting is the lower risk of the
two -- it adds two API fields and a log line, and deliberately leaves the
effective reading, the display and the stall check exactly as they were. The
socket change alters how the web server retires connections under load, which
is the kind of thing that wants a miner left running for a day rather than
three minutes.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place. `SHA256SUMS` covers
every file here; check it before you flash something you downloaded.
