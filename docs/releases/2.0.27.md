## Pool B can ask for extranonce updates

Reported by an owner: there was no extranonce subscribe for pool B. Correct,
and the setting turned out to be half-built. The NVS key existed and was read
at startup into a field that nothing in the firmware ever looked at again;
there was no way to set it over the API, no control in the interface, and the
pool B task never sent `mining.extranonce.subscribe`. Pool A and the fallback
have always done this properly.

Pool B could always *receive* a rotation — the handler has been in that task
the whole time. It simply never asked for one. Against a pool that rotates
extranonce, pool B keeps the value it was handed when it subscribed, its work
goes stale, and its shares are refused. That reads as the pool misbehaving.

The switch is beside pool B's TLS toggle on the Dual Pool tab, and it appears
on boards that report extranonce support — the BC04, where dual mining is
actually used.

## Two more, found while fixing that one

**Saving the pool page turned pool B's TLS off.** `poolBTLS` was accepted and
stored, but never reported back, so the interface read it as absent, showed
the switch off whatever the miner was doing, and wrote that back on save.
Anyone who opened the tab and pressed Save disabled TLS on pool B without
being told. The failover switch next to it was reported correctly all along.

**Saving the pool page overwrote the fallback stratum password.** That field
was initialised to the literal string `password` and sent as-is, rather than
using the `*****` placeholder the other password fields use. Opening the page
and saving — without touching the fallback tab — replaced a configured
fallback password with `password`. Solo pools ignore the field, which is
probably why it went unnoticed.

If you have a fallback pool that needs a real password, check it after
updating.

## Still open

**The fan-fault protection cannot fire.** The check is passed a maximum speed
of zero and both its comparisons are against that, so it returns true for any
RPM including zero. The over-temperature and unreadable-sensor trips are the
two thermal protections known to work.

**A BC04 cannot de-energise its own hashboard once the I²C bus is gone.**
A miner showing an empty bus scan, a board temperature of −60 °C, or a reboot
every four minutes should have its power removed by hand.

Both are described in `docs/KNOWN-ISSUES.md`.

## Testing

The firmware half was verified on a BC01 running dual mining against a real
pool, by reading the frames off the wire rather than trusting the setting:
after `pool B connected`, the task sent `mining.configure`, `mining.subscribe`,
`mining.authorize` and then `mining.extranonce.subscribe` on pool B's own id
counter, and the pool answered with an extranonce.

The toggle itself has **not** been seen on screen: it renders only on boards
reporting extranonce support, and no BC04 was available. **No BC04 has run
this firmware at all** — those images are built from the same source and are
untested on hardware.

## Files

`-full.bin` is the whole flash and is what the web flasher writes over USB.
`-ota.bin` and `-www-ota.bin` are for updating in place. `SHA256SUMS` covers
every file here; check it before you flash something you downloaded.
